# 受け入れ条件（下書き）

誰が、どの場面で、何ができれば「できた」と言えるかを、先に決めておく。L2 の評価（`eval/behavior`）と L3 の確認（`docs/verification/desktop-checklist.md`）は、ここの場面を確かめるためにある。M3 で公開するかどうかも、ここを基準に判断する。

> 状態：下書き（2026-11-26）。「判断が要る点」に開発者の返事をもらってから確定する。

## 前提

- 想定する利用者は、技術者ではないビジネスパーソン。部署やチームが自分たちで試し、予算が付いたら WalkOn に導入支援を頼む。
- 使い方は3つの段に分かれる（連載計画の図と同じ）。この文書の対象は1と2。3は本導入として WalkOn が支援する段で、M3 の条件には入れない。
  1. **ひとりで試す**：Claude Desktop に拡張機能を入れ、資料フォルダを選び、チーム用のプロジェクトの中で頼む。
  2. **チームで試す**：共有フォルダ（Google Drive など）に決定の記録を置き、各自のパソコンの承認ページで承認する。
  3. **本導入**：ChatGPT などからも使う、ネット経由のサーバー、権限と監査。
- 合格の条件は、利用者から見て確かめられる形で書く（画面に何が出るか、AI が何を書くか）。

## M3 で公開する条件（案）

1. S1〜S13、S15、S17 が「満たす」になっている。S4、S10、S14、S16 は、満たすか、未実装であることを README に書く。
2. L2：core スイートを版ごとに回し、すべてのケースが3回中3回合格している（`min_pass: 1`）。
3. L3：確認表のすべての項目が、公開する版で合格している。
4. 日本語と英語の README、ADR（`docs/spec-changes.md` から作る）、凍結したインターフェース v0。

## 決まったこと（11/26）

- **5分デモは、技術者ではなくビジネスパーソン向けにする。** 初見の人が5分以内に、拡張機能とデモのデータで、取引先あての文面を正しい価格で書かせるところまで行ける。docker compose は開発者向けとして残す（S1〜S3 の合格条件に含める）。
- **管理画面は、チームの権限を扱う段で必要になる。** v0.2 の M5 はその想定だった。

## 判断が要る点

1. **ベンダーに縛られないこと（ChatGPT など）を、M3 でどこまで見せるか。** 開発者の考え：シェアの上で ChatGPT は必要。RAG やベンダーに縛られないところに優位性がある。M3 の条件の形を、言葉の定義とあわせて決める。
2. **チームの段（段2）で、承認する人の設定を誰がどう行うか。** 今は `.coheads/team.json` を手で書く形で、技術者でない人には向かない。管理画面（権限）の最初の一部として、承認ページで設定できるようにするか。
3. **Windows を M3 の条件に入れるか**（S1）。
4. **Word と PDF を読むか**（S2）。案：M3 の条件に入れる。
5. **L2 の合格の基準。** 案：取引先あての文面（S5、S7、S8）は3回中3回、それ以外は3回中2回。
