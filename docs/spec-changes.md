## SC-01 「現行」を、状態ではなく有効期間で判定する
- 状態：確定（11/25）
- 変更：決定の「状態」（候補・承認済み・失効など）は、台帳上の扱いを表すものとして残す。「その日に有効か」は、有効期間（適用日と失効日）で判定する。
- 理由：状態だけで判定すると、適用日の前に承認された決定を扱えない。
  - 例：12万円が現行のときに、「12/1から13万円」が11/30に承認された場合。11/30の時点では12万円を現行として返す必要があるが、状態はどちらも「承認済み」になる。
- 根拠：自動テストの値上げ予約のシナリオ。状態だけで判定する実装では、11/30時点の現行を正しく出せなかった。直した後は、適用日の前後と、過去の任意の日付での再現が合格した。
- 反映：インターフェースv0 §3の規則、コアの台帳。

## SC-10 案件名のない依頼でも、資料の検索結果から案件を推定する
- 状態：試行中（11/26）。自分のフォルダを使う形では既定で有効、デモと試験では無効（SB_MATCH_BY_SEARCH）。
- 変更：依頼に案件名・別名・担当者名がないとき、参照できる案件の資料を検索する。上位3件の関連する結果がすべて同じ案件か、関連する結果が1件だけで強く一致したときに限り、その案件と判断する（matchedBy 'search'）。判断したことは、注意として返す。
- 理由：使っている感覚なく使えるようにするため。自分のフォルダで試す人は、依頼のたびに案件名を言わない。
- 根拠：フォルダでの試験。「交通費の締めは？」は「社内」、「提案価格はいくらで確定した？」は資料のある案件と判断した。「来週の定例会議のアジェンダを作って」と「今日の天気は？」は、何も返さなかった。
- 注意：仕様の「案件が特定できないときは何も返さない」は、この条件を満たさないときに引き続き適用する。検索の点数は質問の言い回しで低くなるので、1つの点数ではなく、上位の結果がそろうかで判断している。

## SC-16 裏側の働きを表に出さない（方針）
- 状態：確定（11/26）
- 方針：Coheadsの仕組みは裏側で働かせ、利用者の目には出さない。名前を出すのは、利用者が自分で探したり設定したりする場所だけにする（拡張機能・プラグインの一覧、ツールの権限、承認ページのタブ名）。判断が分かれたときは、作る側の都合（名前を見せたい、など）より、利用者の使い勝手を優先する。
- 変更：

## SC-17 資料どうしの金額の食い違いを知らせる
- 状態：実装済み（11/26、0.3.3）
- 背景：台帳がまだ空のチーム（入れた初日）では、承認された決定がないため、古い提案書の10万円と新しい承認メモの12万円のどちらもAIに「関連資料」として渡るだけだった。どちらを使うかはAIの判断に任されていた。
- 内容：
  - 案件が特定でき、その案件に承認済みの金額の決定がないとき、案件の資料すべて（宛先の上限の範囲内）から、価格の言葉（価格・料金・見積・月額など）と一緒に書かれた金額を拾う。
  - 金額が2種類以上あれば「■ 資料どうしの食い違い」の節を出す。金額ごとに、書かれている資料・日付・その行と、書きぶり（決定・承認と書かれている／未決・案と書かれている／旧い値として書かれている）を並べる。
  - 注意に「どの金額も確定として書かず、どれで進めるかを利用者に確認する。決まったら承認待ちの候補として記録できる」を入れる。最も新しい記載も示す（旧い値としての記載は除く）。
  - 承認済みの金額が台帳にあるときは出さない。その場合は、現行の決定と、資料への注釈（「この資料の金額は現行ではない」）で足りる。
  - フックで差し込む文面も同じものを使う。プロジェクトの指示とスキルは変えていない（利用者が設定し直す必要はない）。

## SC-18 食い違いの中に「決定」と書かれた資料があれば、候補の下書きを添える
- 状態：実装済み（11/26、0.3.4）
- 背景：SC-17をClaude Desktopで試した（11/26、1回）。AIは金額を確定として書かず、10万円と12万円のどちらで書くかを選択肢で聞いた。利用者が12万円を選ぶと、そのメールを書き、「承認待ちの候補として記録しておけます」と申し出た。ただ、資料に「承認者：佐藤」と書いてあっても、記録するには金額・単位・適用日をもう一度そろえる必要があった。
- 内容：
  - 食い違いの中で最も新しい記載が「決定・承認と書かれている」資料なら、その資料から候補の下書きを作ってAIに渡す。中身は、案件、論点（提案価格など）、金額、課金の単位、税の扱い、適用日、根拠の資料ID、資料に書かれた承認者。
  - AIは、利用者に記録するかを聞き、望まれたら下書きのまま候補を出す。資料に書かれた承認者は参考として示すだけで、承認にはしない。承認は、チームの承認者が承認ページで行う。
  - 候補を出すときの根拠に資料IDを渡すと、資料の題名つきで記録され、承認ページに題名が出る。
  - 同じ案件に承認待ちの金額の候補があるときは、下書きを出さず、「承認待ち」と利用者に伝えるようにした。候補が二重に出ないようにするため。
  - スキル（プラグイン0.3.2）にも、食い違いのときは利用者に聞く、選ばれたら記録するかを聞く、という手順を足した。
- 試験：core/test/conflicts.test.ts に、下書きの中身、候補がある間は下書きを出さないこと、を足した。全26件が通る。作った拡張機能をNodeで起動し、下書き → 候補の登録 → 次の問い合わせで下書きが消え承認待ちと伝える、の流れを確かめた。
- 範囲：下書きは、資料1件の書き方から読み取る。適用日や単位が書かれていなければ空のままにする。
- Claude Desktopでの結果（11/26、チーム用プロジェクトの中、台帳が空の試し用フォルダ、1回）：
  - 「台帳」「Coheads」の言葉は出なかった（0.3.3では2回続けて「決定台帳」と書いていた）。
  - 金額は聞かずに、月額120,000円（税別）でメールを書いた。根拠に「11/24の価格承認記録（承認者：佐藤さん）」を挙げ、10月の提案書の100,000円から変わる理由を本文に一文入れ、正式な記録がまだないことを伝えて、承認待ちの候補として記録するかを聞いた。
  - 指示（どれで進めるかを利用者に確認する）とは違う動き。候補の下書きを添えたことで、AIが最新の承認記録の金額を正として扱ったとみられる。
- 続き（11/26、同じ条件）：「記録して」で候補が記録され、承認ページで承認すると、新しいチャットでは「現在のチームの決定」として12万円で書いた。どのチャットにも出していない13万円をチャットを通さずに記録・承認すると、新しいチャットは13万円で書いた（取得元がCoheadsであることの確認。詳しくは docs/verification/desktop-checklist.md）。
- 0.3.5：AIが承認日と適用日を混同した（「11/24に承認」。実際は11/26承認、11/24から有効）ため、現行の決定の行に「チームで11/26に承認」を出すようにした。
- 0.3.6（11/26実装。確定は L2 の評価の後、SC-19）：食い違いのときの指示を2つに分けた。
  - 最も新しい記載が「決定・承認」と書かれ、承認者の名前もある資料なら、その金額で書いてよい。根拠の資料（日付と題名）と、チームの正式な記録はまだないことを利用者に必ず伝え、記録するかを聞く。
  - それ以外（未決・案と書かれている、決定の書きぶりや承認者の名前がない）は、金額を書く前に、どれで進めるかを利用者に聞く。
  - 理由：根拠のある金額まで毎回聞くのは手間になる。根拠と「正式な記録がない」ことを伝えれば、利用者は誤りに気づける。0.3.4での動き（聞かずに12万円で書き、根拠と記録がないことを伝えた）を、指示として正式にした。
  - スキル（プラグイン0.3.3）も同じ内容にした。試験に「承認者の名前がない資料なら先に聞く」を足した。全27件が通る。

## SC-21 資料フォルダの Word と PDF を読む
- 状態：実装済み（11/26、#23）
- 内容：
  - .docx と .pdf の本文を取り出して、.md・.txt と同じように索引に入れる。Claude Desktop 内蔵の Node で動くよう、JavaScript だけのライブラリ（fflate、unpdf）を使う。
  - Word の表は、1行のセルを「 | 」でつないで1行にする。金額と、それが何の金額か（「月額利用料 | 月額120,000円」）が同じ行に残り、食い違いの判定に使える。
  - PDF は、日本語の前後に入る余分な空白（「A 社」「100,000 円」）を取る。日本語の隣の本来の空白も消える（「向け 新サービス」→「向け新サービス」）。検索と金額の読み取りを優先した。
  - 文字のない PDF（スキャンした画像）は、資料として一覧には出し、本文に「文字のない PDF。中身は読めない」と入れる。
  - Office が開いている間に置く「~$」で始まるファイルは読まない。
  - Word と PDF は読むのに時間がかかるため、ファイルの大きさと更新時刻が変わったときだけ読み直す。
  - 資料の ID は、Word と PDF だけ拡張子を残す（「A社/提案書v1.pdf」）。同じ名前の .docx と .pdf を別の資料として扱うため。.md・.txt は今までどおり。
- 残る点：資料の日付は、Word と PDF ではファイルに記録された更新日時（なければファイルの時刻）。本文に書かれた日付（「提案日：2026年10月28日」）は見ていない。変換し直した古い資料が「最も新しい記載」になることがある。


## SC-22 承認ページを、利用者が使う画面にする
- 状態：確定（11/27、開発者の判断を受けて直した）
- 内容：承認ページをタブに分けた（承認待ち／承認する人／ほかの AI に貼る／AI に渡したもの／やめ方とデータ）。画面には仕組みの名前を出さない（ブラウザのタブ名と、拡張機能・プラグインの一覧で探す所だけ）。
  - **承認する人（S12、#22）**：画面で加える・外す。変更は共有フォルダの記録（`.coheads/events/`）に1件1ファイルで書く（`approver_added`／`approver_removed`）。決定の記録と同じ流れで時刻順に再生するので、同期の遅れで順番が前後しても同じ結果になる。承認は「その時点の一覧」で確かめる（あとで外された人が前にした承認は有効のまま）。一覧が空の間は、お試しとしてメンバー全員が承認でき、誰でも最初の1人を加えられる。最初の1人を加えた人も、一覧に入る（自分を閉め出さないため）。名前は、チームの記録に出てくる名前（候補を出した人、承認した人など）から選ぶ。まだ記録に出てこない人だけ、手で入れる（表記ゆれで承認できない人を出さないため）。1人でも載ったら、承認と一覧の変更は、載っている人だけができる。全員を外すと、全員が承認できる状態に戻る。以前の `team.json` は、一覧の最初の値として読む（書く必要はなくなった）。名前は各自の自己申告で、この一覧はチームの約束ごとを画面にしたもの（なりすましを防ぐ仕組みではない。本当の権限管理は本導入）であることを、画面に書いた。
  - **ほかの AI に貼る（S18、#24）**：案件を選ぶと、renderCopyText と同じ文面（見出し「【チームの決定】」）をコピーできる。渡す範囲（機密区分の上限）は Claude に渡すものと同じにした。社外秘（confidential 以上）の案件をコピーするときだけ、「社外秘の案件です。会社が使ってよいと決めた AI にだけ貼ってください」と1回確かめる。作ったことは「AI に渡したもの」に残る。
  - **AI に渡したもの（S16、#26）**：アクセスログの新しい順50件を、日時・できごと・依頼・案件・渡したもの（決定の値、資料名）で出す。依頼の前の自動の確認で何も渡さなかったものは出さない。
  - **やめ方とデータ（S4、#25）**：拡張機能・プラグインの外し方、チーム用プロジェクトの指示文を消すこと、このパソコンのデータの保存場所と中身、消えないもの（資料、共有フォルダの記録）を示す。「このパソコンのデータを消す」で保存場所のフォルダごと消す（確認の印と、確認のダイアログつき。どちらにも「AI に渡したものの記録も消えます」と書く）。拡張機能を入れたままなら、次の依頼で索引を作り直す。
  - 承認ページは、Host が 127.0.0.1／localhost のときだけ答える（ほかのサイトから AI に渡したものの記録を読まれないように）。
  - **新しい版の記録（#1 の最初の一歩）**：この版で読めない種類の記録を共有フォルダに見つけたら、飛ばして数え、承認ページの上と、AI に渡す案件の文面の「注意」に「チームの誰かが新しい版を使っている。更新を」と出す。更新して読めるようになったら、最初から再生して効かせる。
- 開発者の判断（11/27）：
  1. 承認する人の決まりはこの形。ただし、最初の1人を加えた人も一覧に入れる、名前は記録から選ぶ、自己申告であることを書く。
  2. 外される前にした承認は有効のまま。
  3. 貼る文面の範囲は Claude と同じ。社外秘の案件だけ1回確かめる。
  4. 保存場所をまるごと消す。確認の文に「AI に渡したものの記録も消えます」を入れる。
  5. 古い版との混在は受け入れる。この版から、知らない記録を見つけたら更新を促す。
- 理由：SC-20 の「利用者にファイルを直接触らせない」と、S4・S12・S16・S18 の合格条件を満たすため。
- AI に渡す文言：知らない記録があるときだけ、案件の文面の「注意」に1行足す（get_context とフック）。L2：`newer-version-notice`（新しいケース）と `approved-overrides-docs` を各1回、どちらも合格（`eval/behavior/results/0.3.6/2026-11-26T15-14-21-core.md`）。更新の話はメールの本文に入れず、補足で伝えた。
- 残る点：古い版（0.3.6 まで）の Coheads は、承認する人の変更の記録を読まずに飛ばす。チームの全員が新しい版にするまで、古い版の人のパソコンでは一覧が効かない（`team.json` があればそれ、なければ全員が承認できる）。受け入れる（開発者の判断）。

## SC-23 資料から決定の候補を作るときの方針（O-02）
- 状態：方針確定（11/27、開発者の判断）。実装は #21 のあと（#11）。
- 内容：
  1. **保留の扱い**：「保留」の決定は作らない。台帳の現行の値に入れず、決定の候補にもしない。「未確定の事項」として、出典の該当行と一緒に置く。AI は現行として書かず、「未確定」と添えて書く。後で確定を示す資料が入ったら、そのとき候補にする。
  2. **候補にする条件**：確定を表す言葉（承認・決定・適用など）と、承認者の名前がそろった記載だけを候補にする。「案」「検討」「保留」を含む記載は候補にせず、未確定の事項に入れる。v0.2 の仕様の「自動で判断できないものは保留にして管理者に出す」は、「候補にせず、未確定の事項に入れる」に改める。
  3. **候補を出すきっかけ**：新しい資料の金額が、台帳の現行の値と食い違ったとき。SC-17（食い違いを知らせる）を、台帳に現行の値があるときにも広げる。食い違いがなければ候補は出さない。
  4. **見せ方**：「現行／候補／有効日／出典の該当行」を並べた差分の形で、承認ページと AI に渡す文面に出す。有効日は必須にしない（空なら承認した日から有効。いまのまま）。
  5. **会話から**：AI は記録する前に「記録しますか」と聞き、勝手に記録しない（いまのまま）。取引先のメールに引用された古い価格を決定として拾う誤りは、#29 で一緒に扱う。
- 理由：確定していない記載を候補や「保留の決定」として台帳に入れると、承認する人の確認待ちが増え、AI が現行と取り違えるおそれもある。確定していないものは、未確定として AI に渡すほうが、現行を書かないという目的に合う。候補は、承認する人が判断できる材料（確定の言葉と承認者）がそろったものに絞る。
- M3：S20・S21 を、M3 で公開する条件に入れる（11/27、開発者の判断）。実装の順番（#7 → #1 → #21 → O-02）は変えず、0.4.0 の条件には入れない。
- 型：`DecisionStatus` の `on_hold` と、`DecisionEvent` の `put_on_hold` は使わない（M3 で凍結するときに外すかを決める）。未確定の事項（`OpenItem`）に出典の該当行を持たせる形は、実装のときに interface-v0 に足す。
