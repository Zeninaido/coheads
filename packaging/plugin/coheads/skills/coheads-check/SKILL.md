# Coheadsで確認してから書く

チームの決定（価格、納期、条件、方針など）は、Coheadsに、承認された日と有効な期間つきで記録されている。資料やメール、過去の会話に残っている値は、古くなっていることがある。

## 手順

1. **最初にCoheadsを確認する。** メール、ドライブ、過去の会話を探す前に、Coheadsの `get_context` に利用者の依頼文をそのまま渡す。
   - 依頼文の前に「この依頼に関係する、このチームで承認された決定と資料です」という情報がすでに付いているときは、それを使い、`get_context` は呼ばなくてよい。
   - 人の名前しか出てこない依頼でも、利用者に聞き返す前に `get_context` を呼ぶ。担当者の名前から取引先と案件を特定できる。
2. **「現行の決定」を正として使う。** 「失効した旧決定」や、資料の注釈で「現行ではない」とされた値は、現行として書かない。
3. **「未確定」の事項は、確定した事項として書かない。** 日付や金額を推測で埋めず、未定として扱う。資料の記載（「保留」「検討中」など）が未確定として返されたら、書くときは「未確定」と添える。
4. **「現行と違う金額の資料」が返されたら**、チームではまだ承認されていない金額として扱う。承認されるまでは現行の決定の値で書き、新しい金額の資料があることと、承認する人が承認ページで確かめられることを利用者に伝える。取引先あての文面には、承認されていない金額を書かない。
5. **資料どうしで金額が食い違っていると返されたら**、返された注意に書かれたとおりに進める。最も新しい資料に「決定」と承認者の名前があれば、その金額で書き、根拠の資料と「チームの正式な記録はまだない」ことを利用者に伝える。そうでなければ、金額を書く前に、どれで進めるかを利用者に聞く。
6. **資料の本文が必要なときは**、`get_context` が返した資料のIDを `get_document` に渡して読む。
7. **仕組みの名前を表に出さない。** 取引先に送る文面にも、利用者への説明にも、「Coheads」「台帳」「get_context」などの名前は書かない。チームの記録は「チームで承認された記録」「承認待ちの候補」と呼ぶ。出典は「11/24に承認された価格」「A社案件の承認記録」のように、中身で伝える。確認している途中の経過も、利用者には書かない。取引先や案件に関係のない仕事（社内の会議の準備など）では、チームの決定の確認には触れず、「案件が分かればチームの決定を確認して入れます」のような申し出も書かない。
8. **返された「注意」に、チームの誰かが新しい版を使っているというお知らせがあれば**、拡張機能を新しい版に更新するよう、利用者に一度だけ伝える（手順は承認ページの「新しい版」のタブ）。取引先あての文面には入れない。
9. **取引先あての文面に、価格などを変えた理由を書くときは**、チームの記録か資料に「その変更の理由」として書かれていることだけを使う。ほかの金額のときの理由を流用しない。見つからなければ理由は書かず、書くかどうかと中身を利用者に確かめる。
10. **会話の中で新しい決定が出たら**、または利用者が食い違いの中から金額を選んだら、承認待ちの候補として記録するかを聞く。望まれたら `propose_decision` で登録し、承認のページ（Coheadsが返すアドレス）と承認できる人を案内する。承認のページは各自のパソコンの中にあり、ほかに承認のページはないので、それ以外のページやアドレスは案内しない。「候補の下書き」が返されていれば、その値と根拠の資料IDをそのまま使う。承認は人が行う。

## Coheadsにつながっていないとき

`get_context` が使えないときは、そのことを利用者に一度だけ伝える（「チームの決定を確認できませんでした。Claude Desktopの拡張機能が動いているか確かめてください」）。そのうえで、資料から分かる範囲で進め、価格や納期は「要確認」と明記する。
